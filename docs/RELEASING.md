# Releasing Postal Snap

Postal Snap 0.5.0 is **GitHub-only**: signed Windows NSIS, universal macOS DMG/ZIP containing the notarized and stapled app, and Linux x64 AppImage/Flatpak packages. arm64 Linux scripts exist and are optional until a matching signing host ships them. Mac App Store and Microsoft Store scripts exist for later work; they are not a 0.5.0 go/no-go.

At the 2026-10-17 audit, npm audit reported zero vulnerabilities and the RustSec gate passed across 679 locked crates. The pinned GreenMail 2.1.11 integration run passed, including watcher, batched-move, deferred-move, and no-IDLE connection-limit coverage; see the [mail integration report](../artifacts/mail-integration/results.json). The local `npm run test:all` gate passed all 15 phases, and the audit-fix branch adds native and browser regression coverage for worker recovery, snooze accounting, outbox limits, and identity-save races; verification artifacts live under `artifacts/0.5.0/`. The updater is pinned to upstream `plugins-workspace` commit `f36ba7ba` (zip 9.0.3) with `rustls 0.23.46`; [the dependency remediation note](0.5.0-DEPENDENCY-REMEDIATION.md) records the exact overrides. Do not broaden advisory ignores, and keep the RustSec gate closed to every new advisory.

The release is not ready until the live iCloud and Proton Bridge checks, signed target builds, clean install/update/uninstall checks, and remaining native accessibility and platform gates in [the checklist](RELEASE_CHECKLIST.md) are recorded.

Copy `.env.example` to `.env` and provide signing values outside version control. Generate a dedicated Tauri updater key with `npm run tauri -- signer generate`. Store the private key and password in a password manager and in `.env` (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`). Commit only the public key in `src-tauri/tauri.conf.json` (`plugins.updater.pubkey`). Signed prepare and signed tauri-build use that committed minisign key; `TAURI_UPDATER_PUBLIC_KEY` is optional in `.env` and, if set, must match the committed key. Signed builds refuse the placeholder `POSTAL_SNAP_UPDATER_PUBLIC_KEY`.

Install the release-only Rust audit tool with `cargo install cargo-audit --locked`. Run `npm run audit` while online and `npm run workspace:prepare` before starting a release session. Refresh and review bundled filter snapshots with `npm run filters:update` before shipping; `npm run filters:check` must pass on the committed files. See [CONTENT_BLOCKING.md](CONTENT_BLOCKING.md) and [THREAT_BLOCKING.md](THREAT_BLOCKING.md). `workspace:prepare` skips Playwright e2e so signing hosts do not need browsers; `npm run test:all` still runs `npm run test:e2e` unless `SKIP_E2E=1` is set, and each host installs Chromium once with `npm run setup:e2e` (CI installs it itself). Run `npm run test:mail-integration` with Docker and OpenSSL available; it starts pinned GreenMail 2.1.11 with test-only TLS, runs the ignored Rust protocol suite, and removes the service afterward. CI repeats the format, lint, type, test, build, GreenMail, npm-audit, and RustSec gates. Current Tauri transitive advisories from its Linux GTK3 and URL-pattern graphs are explicitly acknowledged in `scripts/audit-cargo.js`; every new vulnerability, unsoundness, or maintenance warning fails the gate. Review and remove acknowledgements whenever Tauri updates its graph.

`dotenv -e .env -- ...` still exports the signing environment to the whole build tree because the Tauri CLI, its bundler, and the Windows `signCommand` read those variables directly. Vite is restricted to `VITE_`-prefixed variables (`vite.config.ts`), and the Authenticode signer and updater signer children receive a scrubbed environment, but treat every signed release host as secret-bearing and use disposable, isolated VMs.

Windows is the only GitHub draft creator (`npm run release:draft`). Mac and Linux `release:wait-draft` poll for up to 30 minutes and never create a second draft. Normal `release:win`, `release:mac`, and `release:linux` entry points prepare the workspace and start a fresh session themselves; `release:linux` dispatches to x64 or arm64 from the signing host architecture, and both architectures must run on their matching hosts. Use a matching `:resume` entry point only after preparation completed on that same host. Prerelease checks for a clean tracked and untracked worktree before and after version sync; release-session start and verify require the same clean tree. `ALLOW_DIRTY_RELEASE` is retired; commit and push recovery changes before preparing a new session. Prerelease also requires stable versions on `main` or beta versions on `beta`, the matching `origin` upstream, a pushed `HEAD`, and valid direct/MAS entitlement plists.

Sessions are bound to the version, tag, commit, platform, architecture, Node and Rust versions, both lockfile hashes, and a digest of the four generated resources bundled by the direct build: `public/licenses.json`, `public/licenses-cargo.json`, `THIRD_PARTY_NOTICES.npm.txt`, and `THIRD_PARTY_NOTICES.cargo.txt`. If one is missing, session start or verification tells you to run `npm run licenses` and start a fresh session. After changing or regenerating those files, start a fresh release session. Sessions expire after 24 hours. A changed checkout/toolchain or stale session must be restarted rather than resumed. The direct macOS builder runs authoritative `plutil` validation before compilation, clears only the current target's old bundle output, and refuses incomplete DMG/updater artifact sets. `npm run validate:macos-entitlements` is also available as a standalone preflight.

Per-platform continue paths match IYERIS: add the rust target, run the `:prepared` signed build, sign with GPG, and upload with `release:finalize`. They do **not** run `release:verify:local` or `release:verify-draft`; those commands require the complete multi-architecture set and would fail the first signing host. Linux continue uses `rust:target:linux:<arch>` plus `build:linux:<arch>:prepared` (not the extra `sync-version`/`licenses` wrapper in `build:linux:<arch>`). `npm run build:linux` is only a local both-architecture convenience that chains `build:linux:x64` then `build:linux:arm64`; signing hosts use the architecture continue paths. Use disposable, isolated signing VMs for `release:*` and the intentionally destructive `b`/`r` reset aliases; never run those reset aliases in a checkout containing work that is not committed and pushed.

Platform builds collect normalized artifacts in `release/`; `release:sign:gpg` adds SHA-256 and detached GPG signatures. `release:finalize` generates and validates updater manifests, then uploads into the GitHub draft without publishing. After every architecture and Flatpak bundle is present, run `npm run release:verify:local` on a complete artifact directory and/or `npm run release:verify-draft` against the remote draft. After the manual checklist is complete, `npm run release:finalize:hard` verifies the remote asset set and publishes. Direct updater payloads match the IYERIS/Zinnia Tauri v2 native set: Windows setup `.exe` plus `.sig`, macOS `.app.tar.gz` plus `.sig`, and Linux `.AppImage` plus `.AppImage.sig` (not `.AppImage.tar.gz`; that file is only for `v1Compatible`). macOS signing inspection follows Zinnia: `codesign --display --verbose=4` stdout+stderr must show `Authority=Developer ID Application:`, a real TeamIdentifier, and Hardened Runtime. Do not add IYERIS/Zinnia DEB/RPM updater targets.

Tag the release commit with a signed annotated tag and verify it before publishing: `git tag -s v0.5.0 -m "Postal Snap v0.5.0"`, `git push origin v0.5.0`, then `git tag -v v0.5.0` must show a valid signature from the release signer.

Treat the unpublished GitHub draft as the release candidate. Do not replace `release:finalize` with `release:finalize:hard` in CI. Automated and mocked tests do not make a release ready. Stable publication remains a deliberate go/no-go after signed-package testing and a live iCloud smoke (`npm run test:icloud`) on a signing host with a dedicated app-specific password.

The update channel is chosen at runtime, not at build time. Every build uses the endpoint `latest-{{target}}-{{arch}}.json`; `scripts/tauri-build.js` bakes no beta endpoint. The `updateChannel` setting (`auto`, `stable`, or `beta`; Settings > Advanced, direct builds only) picks the feed. Auto follows the installed build (a version containing `-` is beta). Beta clients request target `<platform>-beta` and fetch `latest-<target>-beta-<arch>.json`. Beta to Stable never downgrades; it waits for a newer stable release.

Beta builds generate only `latest-<target>-beta-<arch>.json`; those manifests carry both `<platform>-beta` and `<platform>-<arch>` keys. Stable builds generate both `latest-<target>-<arch>.json` and `latest-<target>-beta-<arch>.json`, so beta users move to stable when it is newer and the beta feed never 404s after a stable publish. Publishing a beta synchronizes beta manifests onto the latest stable GitHub release so the `/releases/latest/download/` endpoint remains stable. `release:finalize:hard` uploads those manifests to the stable release while the beta is still a draft and re-runs the sync after publication, so a failed pre-publish sync aborts before the beta becomes public. After a stable hotfix publish, if a newer published beta exists, its beta manifests are re-synced onto the new latest release so the beta feed does not regress. Draft, directory, and live verifiers require the beta manifest set on stable releases.

After publication the reconcile is non-fatal: a failure prints a warning plus the recovery command and the publish still exits 0. Prereleases whose beta manifests lack the `<platform>-beta` key (older tooling) are skipped with a warning. Reconcile reads every page of `/releases` and validates each downloaded beta manifest (schema plus `version` equal to the selected prerelease) before uploading it to the latest stable release. If anything fails after publication, finalize prints the recovery step: `npm run release:sync-beta-manifests -- --from <beta-tag>` re-syncs that beta's manifests (prerelease tags only; the target is always the latest stable release). `npm run test:release-dry-run` drives manifest generation, the stable reconcile decision, and beta sync with a fake `gh` on `PATH` (no network) and writes the recorded call log and manifests to `artifacts/0.4.3/release-dry-run/`. It also runs inside `npm run test:release-assets`.

To cut a beta such as 0.5.0-beta.1: switch to the `beta` branch, set the version to `X.Y.Z-beta.N` (for example `0.5.0-beta.1`), update the top `CHANGELOG.md` section to match, and run the normal `release:*` flow. Prerelease requires beta versions on `beta` and stable versions on `main`.

Linux release builds run from a pinned baseline: Ubuntu 24.04.4 (glibc 2.39) with a WebKitGTK 4.1 package at or above 2.52.6. `npm run preflight:linux` runs before every `build:linux:*:prepared` and Flatpak bundle; it loads an optional `.env` override and refuses a host glibc newer than the baseline (unless `POSTAL_SNAP_ALLOW_NEWER_GLIBC=1` is a deliberate override) and any `pkg-config webkit2gtk-4.1` below 2.52.6, because the AppImage bundles the build host's WebKitGTK renderer. `NO_STRIP=true` is set for the linuxdeploy AppImage path so its bundled strip handles `.relr.dyn` sections on glibc 2.39 and newer. `npm run setup:flatpak` installs the pinned `org.gnome.Platform//50` runtime and `org.flatpak.Builder//stable`; the setup and build scripts use the app's bundled `flatpak-builder`, so a separate host `flatpak-builder` package is not required. `flatpak:bundle` then runs `flatpak-builder-lint --exceptions manifest` and `appstreamcli validate` on `packaging/flatpak/run.rosie.snap.metainfo.xml` when the AppStream tools are installed. Only the Flatpak installs AppStream metainfo. The AppImage relies on host `xdg-utils`/`desktop-file-utils` for mailto registration and ignores registration failures, runs under XWayland because linuxdeploy's AppRun hook exports `GDK_BACKEND=x11`, and needs host GStreamer for received-mail audio/video because `bundleMediaFramework` is off. AppImages need FUSE 2 (`libfuse2` or `libfuse2t64`) to self-mount; `APPIMAGE_EXTRACT_AND_RUN=1` is the fallback. The Flatpak `.flatpak` bundle is a sideloaded artifact with only its detached `.asc` (no embedded signature); verify it with `release:verify:local` and update by downloading the newest bundle from the matching GitHub release.

Microsoft Store and Mac App Store packaging remain available in `package.json` for a later store train. They are out of scope for GitHub 0.5.0. Direct Mac releases use Developer ID signing/notarization through Tauri. Tauri notarizes and staples the application bundle. Postal Snap then submits the UDIF DMG to `notarytool`, staples that ticket, assesses it with `spctl --type install`, validates the app ticket and Gatekeeper execute assessment, verifies the DMG with `hdiutil`, and archives the same app into the ZIP. The GitHub Mac vehicle is the DMG; Gatekeeper assesses that file, not only the inner app. `APPLE_APP_SPECIFIC_PASSWORD` is accepted as a legacy alias for `APPLE_PASSWORD`. Signed Mac builds fail early if `APPLE_SIGNING_IDENTITY` is missing from the keychain; on SSH sessions run `npm run mac:ssh:keychain` first. Direct notarization accepts `APPLE_ID`, `APPLE_PASSWORD`, and `APPLE_TEAM_ID`, and also supports `NOTARYTOOL_KEYCHAIN_PROFILE` or an App Store Connect API key. Mac App Store `altool` uploads pass `@env:APPLE_PASSWORD`. `scripts/mac-keychain-ssh.sh` still passes the login-keychain password as a `security` argument because `security` offers no stdin or keychain-profile alternative; run it only on a dedicated signing VM. `scripts/setup-macos-ci-keychain.sh` is reserved for a future signed-CI or store-signing path; it is not part of the GitHub 0.5.0 train and CI does not sign macOS artifacts.

Direct Windows NSIS installers are signed after `tauri build` with Azure Artifact Signing (Public Trust), using the same `.env` variables as Zinnia/IYERIS. After that Authenticode pass, `tauri signer sign` replaces `.exe.sig` (and the NSIS zip signature when present) so minisign matches the bytes that will be uploaded. Once per Windows VM, run `npm run setup:win:artifact-signing` as Administrator to install Microsoft Artifact Signing Client Tools. `SKIP_WIN_CODESIGN=1` remains the unsigned escape hatch for `tauri:build`/`tauri:dev`; release entry paths that pass `--require-windows-signing` (`build:win:*:prepared` and the `release:win:*` chain) reject it unless `ALLOW_UNSIGNED_WINDOWS=1` is also set, which is reserved for deliberate unsigned artifact checks. When `TAURI_SIGNING_PRIVATE_KEY` is present, `scripts/tauri-build.js` refuses a bundled Windows build unless every Azure Artifact Signing variable is set (or `SKIP_WIN_CODESIGN=1` is explicit), so `npm run tauri:build` can no longer emit an updater-signed but Authenticode-unsigned installer. The signer and verifier both require the Artifact Signing Public Trust EKU `1.3.6.1.4.1.311.97.1.0` in addition to the publisher CN (and exact DN when `AZURE_ARTIFACT_SIGNING_PUBLISHER_DN` is set), and `release:verify:local` on Windows runs the Authenticode verifier against the release set. GitHub CI does not sign Windows artifacts; `npm run release:win` on the signing VM is the release path. Direct macOS still uses Developer ID identities; CI may import those from `APPLE_CERTIFICATE_P12_BASE64`.

Before publishing, smoke-test iCloud with a dedicated account and app-specific password: set `POSTAL_SNAP_TEST_ICLOUD_EMAIL` and `POSTAL_SNAP_TEST_ICLOUD_PASSWORD` in `.env`, then run `npm run test:icloud`. That live connection is a human/signing-host gate; CI does not run it. Validate mailto registration and run the platform certification tools listed in the GitHub-only section of the checklist. `npm run release:verify:local` and `release:verify-draft` require `GPG_KEY_ID` set to the signer's full 40- or 64-character fingerprint; verification reads gpg `VALIDSIG` status and compares the primary-key fingerprint, so a valid signature from any other key is rejected.

Use [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) as the final go/no-go record. Never publish a draft until every required architecture, signature, checksum, and updater manifest has been verified.
